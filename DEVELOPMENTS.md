## Смена вектора (05.11.2026)

Решения, принятые при обсуждении плана (подробности в `FirstPlanMultiverseCards.md`):

- **Общий пул карточек.** У игрока только ссылки на шаблоны, максимум одна копия каждой. `Card` и `CardId` удалены, вместо них `OwnedCard` (шаблон + усиления + осколки + дата получения).
- **Уровней и опыта нет.** Итоговые характеристики: база × коэффициент редкости + усиления (+ бонус за сет). Задача 3 теперь «Усиления, осколки и характеристики».
- **Дубликат превращается в осколки этой карточки**, а не в золото.
- **Усиление стоит осколков и золота.** Золото: C(n) = C0 + a·n + b·n², осколки: S(n) = 1 + n (числа ориентировочные).
- **Гача**: гача-валюта (дёшево) или золото (дороже), общий счётчик гаранта.
- **Конфиги**: карточки и PvE-сценарии в JSON; гача, сеты и цены усилений в константах кода.
- **PvE** — кампания по вселенным с этапами и боссом.
- **Характеристики** остаются HP / ST / DF.
- **После сдачи**: команда из 3 карточек, ежедневные задания, рейтинг и сезоны, доп. характеристики.

## Многопоточность (05.11.2026)

Бот должен отвечать разным игрокам одновременно, поэтому обработка идёт «по полосам»:

- `bot/KeyedExecutor` — 8 однопоточных полос (`USER_LANES` в `Main`). Игрок всегда попадает в одну и ту же полосу по `userId`.
- Апдейты **одного** игрока выполняются строго по очереди (двойной клик по кнопке не даёт гонки и двойного списания), **разных** — параллельно.
- `TelegramBot.consume` только раскладывает апдейты по полосам и сразу возвращается, поэтому поток long polling не блокируется.
- Пул Hikari увеличен до 10 соединений (должен быть не меньше числа полос).
- Реестр команд, каталог карточек и конфиги после старта не меняются; изменяемое состояние в них не добавлять.

Что остаётся опасным: операции, где участвуют **два** игрока (PvP), и любые записи золота. План:

- [ ] Задача 3: точечные методы репозитория вместо полного `save()`: атомарное списание `UPDATE players SET cash = cash - ? WHERE id = ? AND cash >= ?` (проверять число изменённых строк), добавление осколков.
- [ ] Задача 6: в дуэли блокировать строки обоих игроков (`SELECT ... FOR UPDATE`) в порядке возрастания `id`, чтобы не получить взаимную блокировку.
- [ ] Ожидающие PvP-вызовы хранить в `ConcurrentHashMap` или в таблице.

## Подключение PostgreSQL (05.11.2026)

Выбор: **PostgreSQL 17** в Docker, параметры подключения — в `.env`.
Схема версионируется миграциями **Flyway** и применяется автоматически при старте бота.

### Как запустить

1. Нужны Docker Engine и Compose plugin (`docker compose version`).
2. Создать `.env` из шаблона и заполнить `BOT_TOKEN` и `DB_PASSWORD` надёжным паролем (`.env` в `.gitignore`, не коммитить).
3. Поднять базу: `docker compose up -d`.
4. Дождаться `healthy`: `docker compose ps`; логи при проблемах: `docker compose logs -f postgres`.
5. Запустить бота (`Main`). При старте Flyway создаст таблицы.
6. Посмотреть таблицы: `docker compose exec postgres psql -U <DB_USER> -d <DB_NAME> -c "\dt"`.

Полезно знать:
- `docker compose down` — остановить, данные сохраняются (том `pgdata`).
- `docker compose down -v` — остановить **и удалить данные**.
- База слушает только `127.0.0.1`. Если бот тоже в Docker, `DB_HOST` должен быть `postgres`, а не `localhost`.

Карточка игрока пока выводит базовые характеристики эмодзи: ❤️ здоровье, ⚔️ сила, 🛡️ защита. Истёкшее ожидание имени очищается, игроку приходит просьба снова запустить `/start`. ### Схема БД

- `players(id BIGINT PK, name, cash, starter_set_claimed)` — `id` это Telegram user id (`tg:123` → `123`); флаг не позволяет повторно выдать стартовый набор.
- `card_templates(id TEXT PK, name, universe, rarity, base_hp, base_st, base_df, is_starter)` — каталог карточек, синхронизируется из JSON при старте бота. Путь к картинке вычисляется по ID и в БД не хранится.
- `player_cards(player_id → players, template_id → card_templates, hp_boost, st_boost, df_boost, shards, obtained_at)`, первичный ключ `(player_id, template_id)` — карточки игроков. Усиления хранятся как счётчики, характеристики считаются на лету.

### Формат карточек

Каждый файл `src/main/resources/cards/*.json` описывает одну вселенную. Формат как в `Sanrio.json`:

```json
{
  "universe": "Sanrio",
  "cards": [
    {
      "id": "sanrio_badtz_common",
      "name": "Badtz",
      "rarity": "COMMON",
      "hp": 100,
      "st": 16,
      "df": 11,
      "starter": true
    }
  ]
}
```

`id` уникален среди всех файлов и одновременно задаёт имя картинки: `src/main/resources/cards/images/{id}.png`. `rarity` — одно из `COMMON`, `UNCOMMON`, `RARE`, `EPIC`, `MYTHIC`, `LEGENDARY`, `DIVINE`; характеристики — целые числа от 0; `starter` — `true` или `false`. При запуске бот читает файлы, проверяет наличие картинок и синхронизирует шаблоны в PostgreSQL; JSON остаётся источником данных.

### Принятые решения

- Миграции только через новые файлы `V2__...sql`, `V3__...sql`; уже применённые файлы не править. V1 переписана при смене вектора, пока нигде не была применена. Если V1 в старом виде уже запускалась локально, Flyway выдаст ошибку контрольной суммы: `docker compose down -v` и запустить заново.
- `save()` делает upsert карточек: усиления и осколки обновляются, `obtained_at` остаётся прежним. Удалять карточки пока не нужно.
- Новый игрок создаётся с `cash = 0`; карточки из JSON (`starter: true`) и признак выдачи сохраняются одной транзакцией.
- Юнит-тесты не требуют БД, поэтому CI (`mvn package`) работает без Postgres.
